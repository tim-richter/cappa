---
title: Agent review
description: Let a coding agent such as Claude Code judge changed screenshots, fix regressions and approve intended changes.
---

`cappa agent` turns a failed visual run into something a coding agent can review cheaply. Every
changed screenshot is handed to the agent as small crops of each changed region instead of
full-page screenshots. The agent looks at each one and writes a verdict, Cappa folds it back in,
and the agent approves what you confirm — or, because it has your code, fixes what is broken.

Nothing is labelled without being looked at. Cappa's [diff threshold](/configuration) already
absorbs sub-pixel rendering differences, so a screenshot that reaches `changed` differs by more
than your project tolerates. Guessing what kind of change it is from pixel statistics labels
exactly the changes that matter wrongly: a larger font reads as a harmless shift and recolour.

The approach follows [BlazeDiff's agent review](https://www.blazediff.dev/guides/claude-code-visual-review),
adapted to Cappa's plugins and baselines.

## Setup

Install the skill into your project from the directory holding `cappa.config.ts`:

```bash
cappa agent init
```

The files always land in the project root — the nearest directory above with a lockfile or
`pnpm-workspace.yaml` — because that is where agents look for skills. So in a monorepo where only
one package depends on Cappa, run it in that package (`pnpm -F web exec cappa agent init`), and
the skill still goes to the root.

What gets installed depends on the agents the project already uses. You can also pick with
`--stack`:

| Stack | Detected by | Installs |
| --- | --- | --- |
| `claude` | `.claude/`, `CLAUDE.md` (also the fallback) | the skill in `.claude/skills/cappa/`, plus a `cappa-judge` subagent in `.claude/agents/` that judges screenshots in its own context (below) |
| `agents` | `.agents/`, `AGENTS.md` | the skill in `.agents/skills/cappa/` (the vendor-neutral Agent Skills directory, read by Codex and others) |
| `opencode` | `.opencode/`, `opencode.json(c)` | the `.agents` skill, plus OpenCode commands and a judge subagent (below) |

`--stack all` installs everything. The skill is `SKILL.md`, `JUDGING.md` and `MASKING.md`.

The installed files call Cappa the way your project runs it: `pnpm exec cappa`, `yarn cappa`,
`bunx cappa` or `npx cappa`, picked from the lockfile. When Cappa lives in a workspace package,
the command switches into it — `pnpm -C packages/web exec cappa`, `yarn workspace web cappa`,
`bun --cwd packages/web x cappa` or `npm exec -w packages/web -- cappa` — so agents run it from
the root. Override it with `--runner "<command>"`.
Commit the files and tailor them to your project. Re-running `init` skips files you modified,
unless you pass `--force`.

When `cappa.config.ts` has no [`webServer`](/configuration#webserver), `init` points that out:
without one, the agent has to work out how to start your Storybook or app by itself. `init` never
edits the config.

Then ask your agent for a visual review, or run `/cappa` in Claude Code.

### OpenCode

OpenCode reads the skill from `.agents/skills/`. The `opencode` stack also adds commands that run
the review flow, and a subagent that keeps the judging out of your main conversation:

| File | What it does |
| --- | --- |
| `.opencode/commands/cappa-review.md` | `/cappa-review [request]` injects the current `agent check` state. It captures when asked or when nothing is captured yet, hands pending judgments to `cappa-judge`, reports one line per screenshot and offers next steps. |
| `.opencode/commands/cappa-judge.md` | `/cappa-judge [names]` runs the judge as a subtask on the pending screenshots, or on the ones named. |
| `.opencode/commands/cappa-approve.md` | `/cappa-approve <names or label>` approves by exact name or verdict label. It holds back regressions and deletions unless you name them explicitly. |
| `.opencode/agents/cappa-judge.md` | A `cappa-judge` subagent. It reads the region crops and the git history in its own context, and records verdicts with `cappa agent judge`. |

The judge works in a sandbox. It cannot edit files, fetch from the web or start other agents.
Its shell is not narrowed to particular commands: OpenCode's permission patterns match command
text literally, so a list of allowed commands breaks as soon as the runner, the shell or the
quoting differs. Its instructions limit it to `cappa agent check`, `cappa agent judge` and
read-only git (`diff`, `log`, `show`, `status`), so it records verdicts but does not approve,
capture or change code.

The commands and the agent use the runner chosen at install time, because OpenCode runs their
shell steps before the model sees them.

### The judge's model

Judging means reading images. A subagent runs on the model that started it, so if your main
agent uses a model that cannot read images, the judge cannot either. Pin the judge to one that
can with `--judge-model`:

```bash
cappa agent init --judge-model anthropic/claude-sonnet-5-5   # OpenCode: provider/model
cappa agent init --judge-model sonnet                        # Claude Code: alias or model id
```

The model goes into the `model:` field of the judge whose format it matches. `init` refuses a
model that no installed judge can take. Changing the model rewrites the judge without `--force`.
Re-running `init` without the flag keeps the pinned model. Without a pin, `init` warns about the
OpenCode judge. Every Claude model can read images, so the Claude Code judge works without one.

A judge that still finds it cannot see the crops records nothing. It replies with the
`--judge-model` command to run instead of guessing from the region metadata. Don't rely on that
check alone: a model that cannot read images does not always notice. Pinning a vision model is
what makes judging work.

### The Claude Code judge

Claude Code's agent files cannot limit Bash to particular commands, so the Claude Code
`cappa-judge` uses a `PreToolUse` hook instead. Before every shell command the judge runs, the
hook calls `cappa agent guard`, which allows only `cappa agent check`, `cappa agent judge` and
read-only git. It refuses anything else, including chaining, pipes, redirects and command
substitution.

### Large reviews

Each judgment comes with two images, so a single judge cannot take hundreds of them. The skill
gives each judge about 20 screenshots and runs several judges in parallel. Screenshots with the
same `change` line stay with the same judge.

### Two copies of the skill

If the project also has `.claude/skills/cappa`, OpenCode uses that copy of the skill instead of
the one in `.agents/skills`, and `init` points the OpenCode judge at it too. Tailor the `.claude`
copy, and keep `.agents/skills` in sync for other agents.

## How a review runs

1. **Capture**: the agent runs `cappa capture --json` (see
   [machine-readable output](/cli#machine-readable-output)). With a `webServer`, that also starts
   and stops the app under test.
2. **Check**: `cappa agent check --json` writes a judgment request for every changed screenshot,
   which the agent reads instead of the full screenshots:
   - `locator.png`: a thumbnail with every changed region outlined and numbered
   - `regions.png`: one `expected | actual` row per region, cropped with context
   - `overview.png`: expected and actual whole, side by side, when the dimensions changed (in
     addition to the two above when regions were found)
   - `request.json`: the regions (position, size, pixel count), the image dimensions and paths

   The request says where pixels differ, never what kind of change it is: no change types, no
   severity, no suggested label that would prime the judge. Screenshots whose dimensions changed
   are analysed on a canvas padded to the larger size, so their regions are located like any
   other.
3. **Judge**: the agent looks at each change and records a verdict with `cappa agent judge`, then
   re-runs `cappa agent check`, which applies it:

   | Label | Meaning | Next step |
   | --- | --- | --- |
   | `regression-likely` | Broken, clipped, misaligned, resized or reflowed without a code change that explains it | Fix |
   | `intentional-likely` | A deliberate content or style change that matches the code | Approve if intended |
   | `noise-likely` | Non-deterministic content (a clock, random data) or a difference invisible to a user | Mask or approve |

   A screenshot stays pending until it has a verdict. When the `cappa-judge` subagent is
   installed, the agent always hands the judging to it, so a judge pinned with `--judge-model`
   is never bypassed. Without one, an agent whose model cannot read images hands the judgment
   directories to any subagent that can, rather than working from the raw screenshots.
4. **Act** — the agent reports one line per screenshot, asks you to confirm, and approves with
   `cappa agent approve`. A regression can be fixed in code and re-captured with `--filter`.

`cappa agent check` never captures: it reads the screenshots the last `cappa capture` left on disk,
so it is safe to run as often as needed. It works without `diff.interpret` — when a capture did not
persist an interpretation, it is computed on demand.

## In the review UI

`cappa review` shows the verdicts too. Judged screenshots get a verdict badge in the list and
grid views; changed screenshots awaiting judgment have none. The detail page shows the headline, the reasons, the confidence and when the check ran. You can
look at what the agent concluded, agree or disagree, and approve from the same screen.

A verdict is shown only while it still describes the images on disk. Once a screenshot is
re-captured or approved after the check, its verdict disappears until the next
`cappa agent check`. A verdict written with `cappa agent judge` shows up after the next check
applies it.

## Commands

### `cappa agent check`

```bash
cappa agent check --json
```

Prints `{ reportPath, total, passed, changed, new, deleted, pendingJudgments, results }`, where
`results` holds one entry per non-passing screenshot:

```json
{
  "name": "example/button/primary",
  "category": "changed",
  "change": "2 regions @ center (1.20%)",
  "pending": true,
  "judgment": "/abs/screenshots/.cappa-agent/judgments/example/button/primary"
}
```

`change` says only where and how much changed. The same change produces the same text on every
screenshot, which hints at one shared cause, such as a footer date or a theme toggle, for the judge
to confirm. Once judged, an entry carries `verdict: { label, headline, action }` instead of
`pending` and `judgment`. The full report, with regions and absolute paths, is written to
`reportPath`.

| Option | Description |
| --- | --- |
| `--max-tile-regions <n>` | Regions rendered into each `regions.png` (default 8). |
| `--json` | Print the summary as JSON and nothing else. |

Exits with `1` while any screenshot is changed, new or deleted, like `cappa status`.

### `cappa agent judge`

```bash
cappa agent judge example/button/primary --label regression-likely \
  --headline "Submit label truncated" --rationale "'Submit' renders as 'Subm'" --confidence 0.9 --json
```

Records a validated verdict for one or more screenshots with a judgment request. `--label` is
`regression-likely`, `intentional-likely` or `noise-likely`. Passing several names records one
shared verdict.

A verdict is tied to a fingerprint of the expected and actual images it was made about. When a
re-capture changes either image, the verdict is dropped and the screenshot is judged again.

### `cappa agent approve`

```bash
cappa agent approve example/button/primary --json
cappa agent approve --label intentional-likely --json
```

Approves screenshots by **exact** name — unlike `cappa approve --filter`, which matches substrings —
or every changed screenshot whose current verdict carries a label. A screenshot awaiting judgment
has no label, so `--label` never approves it. Refused when `CI` is set, so
baselines only change on developer machines.

It also refuses any screenshot whose current verdict is `regression-likely`. If the change was
intended, judge it `intentional-likely` first. To approve a regression anyway, pass
`--allow-regression`.

### `cappa agent init`

Installs the skill files described in [Setup](#setup). `--stack`, `--runner` and `--force` are
covered there; `--judge-model <model>` pins the judge subagent to a model that can read images
(see [The judge's model](#the-judges-model)).

## Files

Everything lives in `<outputDir>/.cappa-agent/`, which carries its own `.gitignore` — judgments are
only valid for the screenshots on the machine that made them.

```
.cappa-agent/
├── report.json
└── judgments/<screenshot name>/
    ├── request.json
    ├── locator.png
    ├── regions.png
    ├── overview.png     # only when the dimensions changed
    └── verdict.json     # written by `cappa agent judge`
```
