The `cappa.config.ts` file controls how screenshots are captured, stored, and reviewed. Config files
export a configuration created with `defineConfig` from `@cappa/core`.

`defineConfig` accepts either an object or a function that receives a `ConfigEnv` object with the
current CLI command, mode, and environment variables. This is useful when you need to tailor the
configuration in CI environments.

```ts
import { defineConfig } from '@cappa/core';
import { cappaPluginStorybook } from '@cappa/plugin-storybook';

export default defineConfig(({ env }) => ({
  outputDir: env.CAPPA_SCREENSHOT_DIR ?? 'screenshots',
}));
```

## outputDir

- **type**: `string`
- **default**: `'screenshots'`

Folder where screenshots and diffs are written.
Cappa will create actual, expected, and diff directories within this folder.

You most probably want to exclude the actual and diff directories from your version control system.

## retries

- **type**: `number`
- **default**: `2`

The number of times to retry a screenshot if it fails. See the [Screenshot retries](/cappa/screenshot-retries) guide for more information.

## concurrency

- **type**: `number`
- **default**: `1`

The number of parallel browser contexts to use when taking screenshots. Each context can process screenshots independently, significantly speeding up large screenshot runs.

Higher values will consume more system resources (CPU and memory).

## logConsoleEvents

- **type**: `boolean | 'error' | 'warn' | 'info' | 'log' | 'debug'`
- **default**: `true`

Controls which browser console events are logged while captures run.

- `true` logs every console message at the CLI's debug level (only visible with `--log-level 4` or higher).
- `false` disables console logging.
- A severity (`'error'`, `'warn'`, `'info'`, `'log'`, `'debug'`) logs only messages at or above
  it, at the matching CLI level. `'error'` surfaces `console.error` / `console.assert` failures
  without raising the log level; `'warn'` adds `console.warn`.

Uncaught page errors are always logged — as errors when a severity is set, otherwise at debug level.

```ts
export default defineConfig({
  logConsoleEvents: 'error',
});
```

## screenshot

Screenshot configuration might get overwritten by plugins or more specific settings, while taking
the screenshot.

### screenshot.viewport

- **type**: `{ width: number; height: number }`
- **default**: `{ width: 1920, height: 1080 }`

The viewport to use for the screenshots.

### screenshot.fullPage

- **type**: `boolean`
- **default**: `true`

Whether to take a full page screenshot. If `false`, the viewport will be used.

If a height is defined, this setting will supersede the viewport height.

### screenshot.crop

- **type**: `boolean | { root?: string; padding?: number }`
- **default**: `false`

Crop each screenshot to the content actually painted on the page, instead of capturing the whole
viewport (or page, with `fullPage`).

```ts
export default defineConfig({
  screenshot: {
    viewport: { width: 1280, height: 800 },
    crop: true, // or { root: '#app', padding: 4 }
  },
});
```

A small component rendered into a 1920px wide viewport is mostly empty canvas, and that canvas
dilutes every number a diff reports: one changed word is about 0.01% of a 1920×1080 capture, but
several percent of the component. With `crop`, screenshots, diff images and
[`diff.maxDiffPercentage`](#diffmaxdiffpercentage) are about the content.

The viewport is still the size the page is laid out at, so media queries and percentage widths
behave exactly as before. It becomes the most a screenshot can cover, not the size it always has.

What counts as content is what is *painted*, not element boxes:

- text (by its line boxes), images, SVGs, canvases and form controls
- any element with a visible background, border, outline or box-shadow (shadows by their reach)
- anything inside the root, including portals such as popovers and dialogs rendered into `body`

A full-width wrapper `div` with nothing of its own to draw does not stretch the crop; a wrapper
with a background colour does. Hidden and fully transparent subtrees are ignored, and descendants
of an element with `overflow: hidden` are clipped to it.

- `root` — CSS selector of the element whose content is measured (default `body`). Its own
  background and border are not counted, only what is inside it.
- `padding` — space kept around the content, in CSS pixels (default `8`), for paint that has no box
  of its own, such as text shadows or pseudo-elements.

When nothing is painted (or `root` matches nothing), the uncropped screenshot is taken.

:::note
Turning `crop` on changes the size of every screenshot, so existing baselines all show as changed
once. Capture and approve them in one go.
:::

Plugins can override `crop` per plugin, per story / page and per variant.

## diff

Diff configuration sets global comparison settings for screenshots.

`diff` supports two algorithms via `diff.type`:

- `"pixel"` (default) for 'traditional' pixel-count based comparisons
- `"gmsd"` for 'gradient magnitude similarity deviation' comparisons. 
Measures gradient similarity, not just pixel differences. Closer to human perception of similarity.

### diff.type

- **type**: `"pixel" | "gmsd"`
- **default**: `"pixel"`

Selects which algorithm is used when comparing screenshots.


### diff.threshold

- **type**: `number`
- **default**: `0.1`
- **range**: `0-1`

This affects how similar a pixel needs to be to the reference image to be considered the same.

### Pixel-only options

The following options apply when `diff.type` is `"pixel"`.

### diff.includeAA

- **type**: `boolean`
- **default**: `false`

Whether to include anti-aliased pixels in the diff count.
For most users this should be false, because it makes comparisons very sensitive to sub-pixel differences of
fonts and other UI elements.

### diff.fastBufferCheck

- **type**: `boolean`
- **default**: `true`

Whether to use a fast buffer comparison for identical images. This is a performance optimization that
skips the slower image comparison algorithm.

### diff.maxDiffPixels

- **type**: `number`
- **default**: `0`

The maximum number of different pixels before the comparison fails.

### diff.maxDiffPercentage

- **type**: `number`
- **default**: `0`
- **range**: `0-100`

The maximum percentage of different pixels before the comparison fails. This is a relative value,
so it is affected by the size of the images. A 100px image with a 10% difference is 10 pixels different,
but a 1000px image with a 10% difference is 100 pixels different. On very large full page screenshots
this can mean that small changes still slip through. Cropping to content with
[`screenshot.crop`](#screenshotcrop) keeps the percentage about the content rather than the canvas.

#### Screenshots that changed size

Two screenshots of different sizes are compared on a canvas padded to the larger width and height,
both anchored top-left. Each image is padded with its own background (the most common colour on the
edge being extended), so only real content in the grown area counts: a list that gained one item
diffs as that item, and the diff image shows where. A size change never passes, whatever the
thresholds — the change of size is itself the finding.

### diff.interpret

- **type**: `boolean`
- **default**: `false`

Run a structured interpretation pass after the raw pixel diff. Instead of only telling you
*where* pixels differ, interpretation describes *what* changed — additions, deletions, color
shifts and content changes — grouped into regions, each with a position, a percentage and a
confidence score, plus an overall severity (`Low` / `Medium` / `High`) and a human-readable
summary.

```ts
export default defineConfig({
  diff: {
    type: 'pixel',
    interpret: true,
  },
});
```

When enabled, each changed screenshot gets a `diff/<name>.json` sidecar next to its diff image:

```json
{
  "numDiffPixels": 17904,
  "percentDifference": 1.87,
  "interpretation": {
    "summary": "Moderate visual change detected (1.87% of image, 3 regions). Content changed: 1 region (center).",
    "severity": "Medium",
    "totalRegions": 3,
    "diffPercentage": 1.87,
    "width": 1200,
    "height": 800,
    "regions": [
      {
        "changeType": "ContentChange",
        "position": "center",
        "percentage": 0.9,
        "bbox": { "x": 420, "y": 300, "width": 360, "height": 200 }
      }
    ]
  }
}
```

The sidecar is read back by `cappa capture`, `cappa status` and the review UI:

- **`cappa capture`** prints the same breakdown after the failure report, so CI logs show what
  changed and where without downloading the diff images.
- **`cappa status`** prints a per-screenshot breakdown of changed screenshots with severity,
  region count, summary and the individual regions.
- **The review UI** shows a severity badge, a summary banner and interactive, color-coded
  region overlays on the diff view.

The sidecar lives in the `diff` directory, so it is cleared before each capture and removed when
a screenshot is approved.

:::note
Interpretation is pixel-diff only. It is ignored when `diff.type` is `"gmsd"`.
:::

### GMSD-only options

The following options apply when `diff.type` is `"gmsd"`.

### diff.downsample

- **type**: `0 | 1`
- **default**: `0`

Downsample factor used by GMSD.

### diff.c

- **type**: `number`
- **default**: `170`

Stability constant used in the GMSD equation.

### Diff PNG metadata

Generated PNG files include textual metadata (`tEXt` chunks) with the comparison details. This includes:

- `cappa.diff.algorithm` (`pixel` or `gmsd`)
- the configured diff options used for that comparison, stored as `cappa.diff.<option>`

You can read these fields in custom tooling to audit how a diff image was produced.

## review

Configuration for the review UI.

### review.theme

- **type**: `'light' | 'dark'`
- **default**: `'light'`

Color theme for the review UI. Set to `'dark'` for dark mode.

```ts
export default defineConfig({
  review: {
    theme: 'dark',
  },
});
```

### review.port

- **type**: `number`
- **default**: `3000`

Port for the review UI server. Set to a different value if port 3000 is already in use.

```ts
export default defineConfig({
  review: {
    port: 4000,
  },
});
```

### review.browserIdleTimeout

- **type**: `number`
- **default**: `300000` (5 minutes)

How long the browser stays alive between captures started from the
[interactive UI](/interactive-ui), in milliseconds.

Keeping it warm makes an interactive capture feel immediate instead of paying browser startup
on every click; evicting it once idle stops a forgotten review session holding a browser
process indefinitely. Set it to `0` to shut the browser down after every run.

This only affects `cappa review` — `cappa capture` starts and stops a browser per invocation
either way.

```ts
export default defineConfig({
  review: {
    browserIdleTimeout: 60_000,
  },
});
```

## webServer

- **type**: `WebServerConfig | WebServerConfig[]`
- **default**: `undefined`

The app under test — a Storybook, a preview server — that Cappa starts before capturing and stops
when it is done. The URL already lives in your plugin config; this puts the command that brings
it up next to it, so neither you, your CI pipeline nor a coding agent has to start it by hand.

Not to be confused with Cappa's own review server (`cappa review`, `cappa serve`,
[`review.port`](#reviewport)): `webServer` is what the plugins point at.

```ts
import { defineConfig } from '@cappa/core';
import { cappaPluginStorybook } from '@cappa/plugin-storybook';

export default defineConfig({
  webServer: {
    command: 'pnpm storybook --ci',
    url: 'http://localhost:6006',
  },
  plugins: [cappaPluginStorybook({ storybookUrl: 'http://localhost:6006' })],
});
```

| Field | Default | |
| --- | --- | --- |
| `command` | — | Shell command that starts the server. Runs through a shell, so `&&` works on Windows too. |
| `url` | — | Ready once it answers with a 2xx or 3xx status. |
| `reuseExistingServer` | `!process.env.CI` | Use a server that is already answering at `url` instead of running `command`. When `false`, an answering `url` is an error. |
| `timeout` | `60000` | How long `url` may take to become ready, in milliseconds, measured from when `command` starts. |
| `cwd` | directory of `cappa.config.ts` | Where `command` runs. A relative path resolves against the config file's directory, not the current directory. |
| `env` | `{}` | Environment variables, merged over the inherited ones. |

Pass an array to start several servers. They start in parallel, and all of them must be ready
before anything is captured — including for a `--filter` run, since Cappa does not know which
plugin needs which server.

### When it runs

The server starts on the first capture, not when Cappa starts, and every run logs which way it
went: `Reusing server at …` or `Started \`…\``. When screenshots look like a stale build or another
branch, that line tells you whether Cappa ran your command at all.

- `cappa capture` stops the server when the capture ends.
- `cappa review`, `cappa serve` and `cappa capture --watch` keep it running alongside the warm
  browser, and stop it after the same [`review.browserIdleTimeout`](#reviewbrowseridletimeout).
  The next capture starts it again — and rebuilds, so it picks up your changes.
- With `cappa capture --server`, the host starts the server, from its own config.

A reused server is never stopped: Cappa did not start it. A server that Cappa started is stopped
together with every process it spawned, so nothing is left holding the port. If it exits during
a run, the captures that fail because of it say so — with the end of its output — and the next
run starts it again.

The server's output is kept out of the terminal. It is shown when the server fails to start or
does not become ready in time, and streamed live with `--log-level 4`.

### Build, then serve

`command` can build first. `timeout` covers the build, so raise it:

```ts
export default defineConfig({
  webServer: {
    command: 'pnpm build-storybook && pnpm dlx http-server storybook-static -p 6006 --silent',
    url: 'http://localhost:6006',
    timeout: 180_000,
  },
});
```

Reusing a server skips the whole command, build included. Locally that means an already running
Storybook is captured as it is. Use [a function config](/configuration) to pick a dev server
locally and a static build in CI:

```ts
export default defineConfig(({ env }) => ({
  webServer: env.CI
    ? {
        command: 'pnpm build-storybook && pnpm dlx http-server storybook-static -p 6006 --silent',
        url: 'http://localhost:6006',
        timeout: 180_000,
      }
    : { command: 'pnpm storybook --ci', url: 'http://localhost:6006' },
}));
```

### Monorepos

When `cappa.config.ts` lives in one package and the app in another, let the package manager find
the app. This does not depend on the folder layout, and works the same with `npm -w`,
`yarn workspace` or `turbo`:

```ts
webServer: {
  command: 'pnpm -F @acme/web storybook --ci',
  url: 'http://localhost:6006',
},
```

Or run the package's own script from its directory:

```ts
webServer: {
  command: 'pnpm storybook --ci',
  cwd: '../../apps/web',
  url: 'http://localhost:6006',
},
```

Both work whether Cappa runs from the repository root or from inside the package.

Turborepo's interactive UI expects a terminal, so pass `--ui=stream`
(`turbo run storybook --filter=@acme/web --ui=stream`) or call the package manager directly.

### Unreachable URLs

When a capture cannot connect to the app at all, Cappa reports it once rather than once per
task, and says what to do: start it, or add a `webServer` if there is none.

## onFail

- **type**: `(screenshots: FailedScreenshot[]) => void | Promise<void>`
- **default**: `undefined`

Runs after a capture completes in CI mode when there are screenshots that failed comparison. CI mode
is enabled by running `cappa capture --ci` or by setting `CI=true` in the environment. The callback
receives an array of failing screenshots, including both relative and absolute paths to the actual,
expected, and diff images. Use this hook to upload diff images to object storage or integrate with
CI systems.

```ts
import { awsS3Upload } from 'aws-sdk';

onFail: async (screenshots) => {
  // Upload diff images to your storage provider
  for (const screenshot of screenshots) {
    if (screenshot.absoluteDiffPath) {
      await awsS3Upload(screenshot.absoluteDiffPath);
    }
  }
}
```

## browser

The browser screenshots are taken in. The block is shaped like
[Vitest browser mode's](https://vitest.dev/config/browser/playwright): a `playwright()` provider
with `launchOptions`, `connectOptions` and `contextOptions`, plus `headless` and `instances` beside
it. A `connectOptions` block written for Vitest can be pasted here unchanged.

```ts
import { defineConfig } from '@cappa/core';
import { playwright } from '@cappa/core/playwright';

export default defineConfig({
  browser: {
    provider: playwright({
      launchOptions: { args: ['--font-render-hinting=none'] },
      connectOptions: {
        wsEndpoint: process.env.CAPPA_BROWSER_WS, // unset → local launch
        exposeNetwork: '<loopback>',
      },
      contextOptions: { deviceScaleFactor: 1, colorScheme: 'light' },
      actionTimeout: 10_000,
    }),
    headless: true,
    instances: [{ browser: 'chromium' }],
  },
});
```

Leaving `browser` out behaves exactly as before: a local headless Chromium. `playwright` is also
exported from `@cappa/core` itself.

### browser.headless

- **type**: `boolean`
- **default**: `true`

Whether to run the browser in headless mode. Also forwarded to a remote browser server.

### browser.instances

- **type**: `[{ browser: 'chromium' | 'firefox' | 'webkit' }]`
- **default**: `[{ browser: 'chromium' }]`

Which browser to capture with. Exactly one entry for now — more than one is a config error.
Capturing with several browsers needs separate `actual/`, `expected/` and `diff/` folders per
browser; the array shape is there so that can arrive without a breaking config change.

### browser.provider

- **type**: `BrowserProvider`
- **default**: `playwright()`

The options of `playwright({ … })`:

#### launchOptions

Passed to [`browserType.launch()`](https://playwright.dev/docs/api/class-browsertype#browser-type-launch).
`headless` is ignored here — use `browser.headless`.

#### connectOptions

Passed to [`browserType.connect()`](https://playwright.dev/docs/api/class-browsertype#browser-type-connect).
Only used when `wsEndpoint` is set; otherwise cappa launches a local browser. `launchOptions` and
`headless` are forwarded to the server in the `x-playwright-launch-options` header, which
`playwright run-server` honours.

#### container

- **type**: `boolean | { cli?, image?, runArgs?, keepAlive?, readyTimeout? }`
- **default**: off

Run the browser in the official Playwright container image for the exact `playwright-core`
version cappa uses — cappa starts it (or reuses a running one) and connects. See
[Running the browser in a container](#running-the-browser-in-a-container).

| Option | Default | |
| --- | --- | --- |
| `cli` | `CAPPA_CONTAINER_CLI` or `'docker'` | Container CLI: `docker`, `podman`, `nerdctl` — anything with docker's `run`/`inspect`/`port`/`pull`/`logs`/`ps`/`rm`. |
| `image` | `'mcr.microsoft.com/playwright:v{version}-noble'` | `{version}` is replaced with the `playwright-core` version. |
| `runArgs` | `[]` | Extra arguments for `<cli> run`, placed before the image. |
| `keepAlive` | `true` | Leave the container running so the next capture connects instantly. |
| `readyTimeout` | `300000` | Milliseconds to wait for the server; the first start pulls the image. |

#### contextOptions

Passed to [`browser.newContext()`](https://playwright.dev/docs/api/class-browser#browser-new-context),
merged over cappa's defaults (`reducedMotion: 'reduce'`, `deviceScaleFactor: 2`). Use it for
`colorScheme`, `locale`, `timezoneId`, `deviceScaleFactor` and friends.

- `viewport` is not accepted — it stays at [`screenshot.viewport`](#screenshotviewport), because
  plugins and stories override it per capture.
- A custom `userAgent` keeps cappa's `CappaStorybook` suffix, which the Storybook addon's
  `isCappa()` relies on.

#### actionTimeout

- **type**: `number`
- **default**: none

Default timeout, in milliseconds, for actions plugins run on the page
([`context.setDefaultTimeout()`](https://playwright.dev/docs/api/class-browsercontext#browser-context-set-default-timeout)).

### Connecting to a remote browser

Screenshots differ between macOS and Linux even with the same Chromium build — font
rasterisation, colour management and the GPU path all change pixels. To make local captures match
CI, render everywhere in the same place: a Playwright server in the official Docker image, with
cappa running on the host.

Start the server. The image tag must match the `playwright-core` version cappa uses (check with
`pnpm why playwright-core`); Playwright refuses a mismatched client, and cappa's error names the
right image.

```bash
docker run --rm --init -it -p 3000:3000 --workdir /home/pwuser --user pwuser \
  mcr.microsoft.com/playwright:v1.63.0-noble \
  /bin/sh -c "npx -y playwright@1.63.0 run-server --port 3000 --host 0.0.0.0"
```

Point cappa at it:

```ts
browser: {
  provider: playwright({
    connectOptions: {
      wsEndpoint: process.env.CAPPA_BROWSER_WS,
      exposeNetwork: '<loopback>',
    },
  }),
},
```

```bash
CAPPA_BROWSER_WS=ws://localhost:3000/ cappa capture
```

With `CAPPA_BROWSER_WS` unset, the same config launches a local browser — so CI can keep
launching its own while developers opt into the container.

`exposeNetwork: '<loopback>'` lets the browser in the container reach `localhost` on your machine,
which is where Storybook or your app runs — requests are tunnelled back through the connection, so
no `host.docker.internal` rewriting is needed. Cappa does not set it for a `wsEndpoint` (neither does
Vitest): a remote browser seeing your localhost should be a decision in your config, not a default.
The exception is a [container cappa starts itself](#running-the-browser-in-a-container).

With `connectOptions.wsEndpoint`, cappa only connects — starting, pulling and stopping the
container is up to you; [`container`](#running-the-browser-in-a-container) does that for you. If the server
restarts while `cappa review` or watch mode keeps the browser warm, the next run reconnects
instead of failing. Under [`cappa serve`](/remote-capture), the host's config owns the
browser, the same way it owns plugins.

### Running the browser in a container

`container` does the version matching for you: cappa reads the installed `playwright-core`
version, runs the official image for it and connects.

```ts
browser: {
  provider: playwright({ container: true }),
},
```

```bash
cappa capture   # first run pulls the image (~1.5 GB); later runs reuse the running container
```

- **Version match is automatic.** The image only supplies the OS, fonts and browsers. The server
  itself is your own `playwright-core`, mounted read-only into the container, so client and server
  are always the same version and the container needs no npm or registry access — which also
  keeps it working behind TLS-intercepting corporate proxies.
- **Localhost works.** `exposeNetwork` defaults to `'<loopback>'` here, because the container is
  cappa's own and listens on `127.0.0.1` only — Storybook on `localhost:6006` is reachable without
  extra config. Set `connectOptions.exposeNetwork` to change it.
- **`wsEndpoint` wins.** With `connectOptions.wsEndpoint` set (e.g. from `CAPPA_BROWSER_WS`),
  no container is started.
- **Podman and friends.** Set `cli: 'podman'` in the config, or `CAPPA_CONTAINER_CLI=podman` to
  switch for just your machine. `runArgs` passes anything else the CLI needs, e.g.
  `['--userns=keep-id']`.
- **Custom fonts.** Build an image `FROM mcr.microsoft.com/playwright:v<version>-noble` with your
  fonts, tag it per version and set `image: 'registry.example.com/playwright-fonts:{version}'`.
- **Lifecycle.** The container keeps running after cappa exits (`keepAlive: true`), named
  `cappa-playwright-v<version>-<hash>`; changing the version, image or `runArgs` starts a new one.
  Remove them with [`cappa browser down`](/cli#cappa-browser-down), or set `keepAlive: false` to
  remove the container when cappa closes the browser.
- **Remote container hosts.** Mounting `playwright-core` needs the container host to see your
  project directory — true for Docker Desktop, OrbStack, Colima, Podman machine and local
  engines, not for a `DOCKER_HOST` on another machine. Use `wsEndpoint` for those.

Upgrading Playwright means a newer Chromium, so expect baseline churn on a bump — re-capture and
approve.
